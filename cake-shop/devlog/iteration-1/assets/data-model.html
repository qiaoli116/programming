Cake Order Desk: the data model is one table

Companion to the business and its life cycle. The data model for the whole life cycle, kept as small as it can be.

The idea. The agents never call each other. They all work on one shared table, orders, with one row per order. The row is created when the customer sends a request and is finished when the order is closed. Each agent does three things:

  1. Find work: look for rows whose status is the one it handles. That status is its inbox.
  2. Do its job: read the columns written before it.
  3. Hand on: fill in its own column and move status on to the next value, which puts the row in the next agent's inbox.

So the database is the hand-off. It also keeps a record of everything: the life of an order is written in its row.

1. The table

-- SQLite. JSON columns are stored as TEXT.
CREATE TABLE orders (
  id           TEXT PRIMARY KEY,  -- 'C-1043'
  status       TEXT NOT NULL,     -- where it is = whose turn
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,

  -- Stage 1 Ordering
  request      TEXT NOT NULL,     -- customer + message
  spec         TEXT,              -- Intake
  quote        TEXT,              -- Pricing
  slot         TEXT,              -- Capacity
  brief        TEXT,              -- Design brief
  review       TEXT,              -- Review router
  approval     TEXT,              -- Baker (only if flagged)
  confirmation TEXT,              -- Confirmer

  -- Stage 2 Production
  plan         TEXT,              -- Production planner
  made         TEXT,              -- Kitchen staff
  qc           TEXT,              -- Photo check
  release      TEXT,              -- Baker release

  -- Stage 3 Fulfillment
  fulfillment  TEXT,              -- Dispatcher
  handover     TEXT,              -- Driver / counter staff

  -- Stage 4 Done
  receipt      TEXT,              -- Closer
  feedback     TEXT,              -- Feedback summariser

  events       TEXT NOT NULL DEFAULT '[]'  -- the log
);
Why it is shaped like this
  • Four plain columns are all the system needs to find and sort orders: id, status and the two timestamps.
  • One JSON column per agent. Each agent's output is a small document, and its shape is that agent's contract. Changing what Pricing returns changes one column, not the schema.
  • One writer per column. Exactly one agent may write each column, and it writes it once. When the baker corrects a price, the correction goes in approval (for example priceOverride), not into quote. Every value can be traced to who wrote it.
  • Columns grouped by business stage. A stage's output is simply "the row, with that stage's columns filled".
  • Empty means not reached yet. A NULL column is a step that has not happened. An order that skips the baker leaves approval empty for ever.
  • The log lives in the row. events is a JSON list, with one entry added on every status change.
  • No other tables. The customer sits inside request. Prices and the cake catalog are config files. The production calendar is worked out from the slot column of other orders (query below).

5. The three queries every part of the system uses

Find work (an agent's inbox)
SELECT * FROM orders
WHERE status = 'PARSED'          -- e.g. Pricing
ORDER BY created_at;

Hand on (one update does it all)

UPDATE orders SET
  quote      = :quoteJson,
  status     = 'PRICED',
  updated_at = :now,
  events     = json_insert(events, '$[#]',
                 json_object('at', :now, 'by', 'pricing',
                             'from', 'PARSED', 'to', 'PRICED'))
WHERE id = :id
  AND status = 'PARSED';         -- only if still my turn

The last line is the safety catch. If two copies of an agent pick up the same order, only the first update changes the row. The second changes nothing and gives up. The status check is the lock, so no separate locking is needed.

Capacity: how full is a day?
SELECT COALESCE(SUM(json_extract(slot, '$.units')), 0)
FROM orders
WHERE json_extract(slot, '$.productionDay') = :day
  AND status <> 'DECLINED';

There is no calendar table. The bookings are the slot values already in the table.

The baker's review inbox

SELECT id, request, spec, quote, brief, review
FROM orders
WHERE status = 'AWAITING_BAKER'
ORDER BY created_at;

An order's history

SELECT value FROM orders, json_each(orders.events)
WHERE orders.id = 'C-1043';
