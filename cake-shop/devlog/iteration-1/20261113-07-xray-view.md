## 1. Why

The app exists to show agents working together, but the customer view only shows the result. The x-ray shows what happens underneath, as it happens.

## 2. The parts map (static)

[assets/architecture.html](assets/architecture.html): the parts in four layers, who may read and write what, and one message ("it's only 10 people") followed through 13 numbered steps. This is the explained version; the x-ray is the live one.

## 3. The x-ray view

A switch in the studio header: **Customer | X-ray**. In x-ray mode the customer view stays on the left, so you can use the app and watch it at the same time. On the right are two panes:

```
┌ MAP ──────────────────────────────────────────┐
│               [Host]                          │
│              /   |    \                       │
│  [Studio]─[API]  [Job board]  [Model]         │
│             |        |       /                │
│          [Store]─[Designer]─[Tools]─[Checker] │
├ CONSOLE ──────────────────────────────────────┤
│ 12:04:01.462 studio   POST …/messages         │
│ 12:04:02.726 host     step → claude-haiku-5-5 │
│ 12:04:04.809 model    ← ask_designer, reply   │
│ 12:04:05.276 board    job 3 queued            │
│ ▾ { "task": "The customer now has 10 …" }     │
└───────────────────────────────────────────────┘
```

**Map.** Nine boxes: Studio, API, Host, Job board, Designer, Model, Tools, Checker, Store. Each box shows only its name. When something moves between two parts, a dot travels along the line between them. A box glows while it is working, with a timer under it ("thinking 1.6s", "job 3 2.4s"). The checker flashes green or red.

**Console.** A timeline with one line per event: time, part, a short label, and the duration where there is one. Click a line to open its data as JSON: the request body, the model's tool calls and token counts, a tool's input, the checker's verdict, or the fields a save changed. It scrolls with new lines, and a Clear button empties it.

## 4. Where the data comes from

The server records a **trace** per order. Each event is "something moved from part A to part B":

```ts
{ seq, at, from, to, label, ms?, data? }   // from/to: one of the nine parts
```

- **Recorded at:**
  - the HTTP routes (middleware);
  - each model step (a wrapper around the provider);
  - each tool call;
  - `check()` and `price()`;
  - job board changes;
  - each save (a wrapper around the store that lists the changed fields).
- **Linked to its order:** the order id travels in an `AsyncLocalStorage` context, so the business code doesn't change shape.
- **Kept in memory:** the last 500 events per order. It is not in the database and is lost on restart. The order's `events` log for the baker stays as it is.
- **Sent to the browser:** `GET /api/orders/:id/trace?t=…&after=<seq>`. The x-ray polls it every 300 ms while it is open, so the host's turn shows live even while the message request is still running.
- **Never included:** the order token, the API key, or the baker's password.
- **Setting:** `XRAY=on` (the default for the demo) shows the switch. `XRAY=off` hides the switch, the route answers 404, and nothing is recorded. Model steps include the prompt, so a real shop would turn it off.
