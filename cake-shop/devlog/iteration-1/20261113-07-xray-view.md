## 1. Why

The point of this app is to show agents working together. Today the customer view shows the outcome: a reply, a handoff line, progress lines and a changed cake. It hides how that happened: which agent ran, what the model was asked and answered, which tool the designer called, what the checker said, and what was saved. Devlog 06's live run was debugged by reading server logs and screenshots afterwards. The x-ray shows the same thing live, next to the customer view.

## 2. The parts map (static)

[assets/architecture.html](assets/architecture.html) has three parts:

1. **The map.** Four layers: people, browser pages, the API, and the back room (host, job board, designer, tools, rules, model provider, store). The edges are the calls between them.
2. **Who may do what.** What each part reads and writes, and what it may not do (the host never writes to the order, the designer never talks to the customer, nothing reaches the store without `check()`).
3. **One message, step by step.** *"actually it's only 10 people"*, followed through 13 numbered stops on the map, with what moves, what is saved and what the customer sees at each step.

The x-ray view draws **the same map, live**. The static page is its legend.

## 3. The x-ray view: what you see

| Pane | Shows | Live behaviour |
|---|---|---|
| **The map** | The parts map from §2, drawn in the page (SVG), with the same boxes | A dot travels along an edge when something moves between two parts. **Model steps** open to show what the model received and returned:
- the agent, the model id, step number, time taken, and tokens in and out;
- the system prompt (collapsed, with its length), the messages of this turn, and the tools offered;
- what came back: its words and its tool calls with their inputs.

**Pause.** A pause button freezes the trace and the map (new lines are still collected and shown as "12 new" when resumed), so a fast sequence can be read. **Replay** plays the last message's trace again on the map, slowly (one step a second), from the recorded trace. Neither changes the server.

The map and trace are in the studio only. The baker's page gets them later if wanted (§8).

## 4. Where the data comes from: the trace

The server records a **trace**: a list of small events per order, each one "something moved from part A to part B".

```ts
interface TraceEvent {
  seq: number;              // per order, increasing
  at: string;               // ISO time with milliseconds
  from: Part; to: Part;     // 'browser' | 'api' | 'host' | 'designer' | 'board' | 'tools' | 'rules' | 'model' | 'store'
  kind: 'http' | 'step' | 'tool' | 'check' | 'price' | 'job' | 'save' | 'warning';
  label: string;            // one line, as in the trace pane
  ms?: number;              // for things with a duration (a request, a model step)
  job?: number;
  data?: unknown;           // the detail shown when a line is opened (trimmed to 20 KB)
}
```

| Kind | Recorded where | Example label | Data |
|---|---|---|---|
| `http` | Express middleware, on the customer routes | `POST …/messages → 200` | method, path, status, ms (never the token) |
| `step` | A **tracing provider** wrapping the real or fake provider | `host step 0 ← ask_designer, reply` | agent, model, step, ms, tokens, system prompt, messages, tools, result |
| `tool` | `runTool` in the designer loop | `set_design size 8in ✓` | input, ok, result text |
| `check` / `price` | `check()` and `price()` calls from the tools and `applyChange` | `check ✓` / `check ✗ not gluten-free` | verdict, reasons, warning / quote before and after |
| `job` | The job board in `team.ts` (`addJob`, `updateJob`, `fail`, `commit`) | `job 3 working` | job id, status, task or report |
| `save` | A **tracing store** wrapping `OrderStore.save` | `saved: brief, design, quote, chat +2` | which columns changed (a field diff against the previous save) |
| `warning` | Where an event of type `warning` is added today | `price removed from the host's words` | text |

**How the order id reaches the code that records.** Most of this code doesn't know which order it is working for (the provider, `check()`). The server keeps the order id in an `AsyncLocalStorage` context, set by the route and by the job runner. The recorders read it from there. Nothing in the business code changes shape; the provider and the store are wrapped, the rest is one `trace(...)` call at each point in the table.

**Kept in memory, not in the database.** The last 500 events per order, for the 50 most recent orders. The event log on the order (`events`) stays as it is: that is the business record for the baker. The trace is a debugging view and is lost when the server restarts.

**To the browser.** `GET /api/orders/:id/trace?t=…&after=<seq>` returns the new events. The x-ray polls it every 300 ms while it is open, independent of the studio's own poll, so the host's turn shows live even while the `POST …/messages` request is still waiting. Server-sent events would be smoother; polling is consistent with devlog 06 and enough here (§8).

## 5. What the x-ray may show

The x-ray shows how the AI was instructed, which is the point of it. That conflicts with a shop that wants its prompts private, so it is behind a setting:

- `XRAY=on` (default in development and the demo): the switch is shown, the trace route answers.
- `XRAY=off`: no switch, the trace route answers 404, and nothing is recorded.

In both cases:
- **Never** shown: the order token, the API key, the baker's password, other orders' data.
- The customer's own contact details (after confirm) are shown as in the row, since only the holder of the link can open it.

## 6. The map in the page

The x-ray map is the SVG from `assets/architecture.html`, moved into a React component with the same boxes and edge ids (`api→host`, `host→board`, …). A trace event names `from` and `to`, which picks the edge to animate. So the static page and the live map can't drift apart: the static page is regenerated from the component's layout data (a small script), or, if that is more work than it saves, kept in step by a test that compares the box ids.

Nothing new is needed in the browser: plain SVG, CSS animation for the dot, no chart library.

## 7. Tests

- **Server:** the trace records the expected sequence for "it's only 10 people" with the fake (http, host step, job queued, save, job working, designer steps, tools, checks, prices, commit save, host report step, job done), in order, with increasing `seq`; `after` returns only newer events; the token never appears in any event (searched as a string); `XRAY=off` gives 404 and records nothing; the ring buffer stops at 500.
- **Browser (fake):** **F16 x-ray.** Open the studio, switch to X-ray, send "actually it's only 10 people". Expect: the trace shows the host step, job 3, two tool lines with check ✓ and the commit save; the map's `designer` box was marked working during the job; opening the `set_design` line shows its input and the checker's verdict; the order row shows `design.size` 8in; switching back to the customer view shows the normal studio; every earlier flow still passes with the switch present.
- **Live:** run F4 with the x-ray open and save a screenshot of each pane, to check that real model steps (tokens, timings, prompts) look right.

## 8. Choices and open questions

| | Choice | Why / alternative |
|---|---|---|
| 1 | The trace is in memory, not stored | It is for watching, not for the record. The baker already has the event log |
| 2 | Polling, not server-sent events | Same as the studio. SSE would make the dots smoother; can replace polling later without changing the trace |
| 3 | Prompts are shown in full, behind `XRAY` | Showing how the agents are instructed is the purpose. Turn it off for a real shop |
| 4 | One switch for the whole x-ray, studio only | Keeps it simple. **Open:** do you also want it on the baker page, or a separate "x-ray of all orders" page? |
| 5 | The map is laid out by hand | Twelve boxes do not need a layout engine |

**Open:** should the x-ray open in the same window (split, as drawn) or as a second window next to the studio? Split is the default here; a second window gives the map more room on a big screen.
