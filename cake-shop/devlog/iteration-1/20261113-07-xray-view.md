## 1. Why

The app exists to show agents working together, but the customer view only shows the result. The x-ray shows what happens underneath, as it happens.

## 2. The parts map (static)

[assets/architecture.html](assets/architecture.html): the parts in four layers, who may read and write what, and one message ("it's only 10 people") followed through 13 numbered steps. This is the explained version; the x-ray is the live one.

## 3. The x-ray window

An **X-ray** button in the studio header opens a separate window (a pop-up, about 1100 × 800). The studio itself does not change: no switch and no split screen. Put the x-ray window on a second screen, or beside the studio, and use the app as normal.

The pattern is the presenter-notes window of the stream decks (`openday/CAIT-AI-deck-handover`, `stream-decks/_kit/deck.js`):

- **Show only.** The window has no buttons, links or inputs, and nothing to click. Its text cannot be selected. The console is never scrolled by hand: new lines appear at the bottom, and old ones drop off the top. Everything you do, you do in the studio.
- **One per studio.** It is opened with a fixed window name (`cake-xray`). Pressing X-ray again brings it to the front instead of opening a second one. If pop-ups are blocked, the studio shows a short hint.
- **The studio feeds it.** The studio polls the trace (§4) and passes each new event to the window with `postMessage`. The window never calls the server, so it needs no token and no code of its own for fetching.
- **It finds the studio again.** The window says hello to its opener every half second until it gets an answer. After that it says hello once a second. If the studio reloads, the window shows "Studio reloading, connecting again…" and picks up where it left off. If the studio is closed, the window says so. It only listens to messages from `window.opener` that carry a `cakeXray: 1` marker.
- **It follows the order.** It shows the order the studio has open. If the studio moves to another order, the window clears and starts again.

The window has a header line (order id, what is happening now, and a connection dot) and two panes:

```

│ [User]───┤[Studio]─┼─┤─[API]   [Job board]            │ │[LLM]      │ │
│          │         │ │   |      [Designer]─[Tools]─[Checker]──────┤   │ │

```

**Map.** Ten boxes, each showing only its name, in three dashed frames that say where each part runs:
- **User**: the person, outside everything.
- **Browser**: Studio.
- **Backend (Node server)**: API, Host, Job board, Designer, Tools, Checker.
- **DB (SQLite)**: drawn as a cylinder below the backend. It is a file the backend reads and writes.
- **LLM (Claude)**: in its own frame, Anthropic API, outside the backend. Both agents call it. When something moves between two parts, a dot travels along the line between them. A box glows while it is working, with a timer under it ("thinking 1.6s", "job 3 2.4s"). The checker flashes green or red.

**Console.** A timeline with one line per event: time, part, a short label, and the duration where there is one. If the event has data, it is shown at once on a dimmer line underneath, as one line of JSON cut to the window width: the request body, the model's tool calls and token counts, a tool's input, the checker's verdict, or the fields a save changed. It keeps the last 200 lines.

## 4. Where the data comes from

The server records a **trace** per order. Each event is "something moved from part A to part B":

```ts
{ seq, at, from, to, label, ms?, data? }   // from/to: one of the ten boxes
```

- **Recorded at:**
  - the HTTP routes (middleware);
  - each model step (a wrapper around the provider);
  - each tool call;
  - `check()` and `price()`;
  - job board changes;
  - each save (a wrapper around the store that lists the changed fields).
- **Linked to its order:** the order id travels in an `AsyncLocalStorage` context, so the business code doesn't change shape.
- **Kept in memory:** the last 500 events per order. It is not in the database and is lost on restart. The order's `events` log for the baker stays as it is.
- **Sent to the browser:** `GET /api/orders/:id/trace?t=…&after=<seq>`. The studio polls it every 300 ms, but only while the x-ray window is open, so the host's turn shows live even while the message request is still running. The studio then posts the new events to the window.
- **Never included:** the order token, the API key, or the baker's password.
- **Setting:** `XRAY=on` (the default for the demo) shows the X-ray button. `XRAY=off` hides the button, the route answers 404, and nothing is recorded. Model steps include the prompt, so a real shop would turn it off.
