# cake-shop: Two agents, a host and a designer

**Date:** 2026-11-13

**Status:** Building

**Iteration:** Iteration 1, Stage 3 Implementation (see [process.html](../../docs/process.html#iteration-1))

**Scope:** Split the design assistant into two agents with separate jobs: a **host** that talks with the customer, and a **designer** that works on the order. They coordinate through a job board on the order, which the customer can see.

**Depends on:** [20261113-05-assistant-tools-and-test-flows.md](20261113-05-assistant-tools-and-test-flows.md) (the tool loop, the shared workspace rules, Undo, the test flows)

---

## 1. Why split

Devlog 05 made one agent that talks and changes the order in the same turn. It works, but:

- **The customer waits in silence.** A turn with tools takes 3 to 8 seconds. Nothing tells the customer what is happening, and the chat is closed until the turn ends.
- **One prompt does two jobs.** Talking well (short, kind, one question at a time) and working well (exact ids, the checker's rules, re-fitting sizes) pull the prompt in different directions.
- **This app demonstrates agents working together.** Two agents with clear roles, a visible handoff, and a shared board are the point of the demo.

For a shop this small one agent would be enough. The split is worth it for the responsiveness and the clarity of each role, and because showing it is the goal.

## 2. The two agents

| | Host | Designer |
|---|---|---|
| Job | Talks with the customer | Works on the order |
| Sees | The chat, the order, the job board, the catalog | One task from the host, the order, recent chat for context, the catalog |
| Tools | `ask_designer(task)`, `reply(text, cant_do, suggestions)` | `set_brief`, `set_design`, `start_design`, `propose_options`, `get_allowed_values`, `check_design`, `report(summary, questions)` |
| Writes to the order | **Never.** It can only ask the designer. | Yes, through the checker, as in devlog 05 |
| Talks to the customer | Yes | **Never.** It reports to the host. |
| Model | Fast (Haiku 5.5) | Strong (Sonnet 5.5) |

The host never says a change is done until the designer has reported it. That keeps the host from promising what the designer could not do.

## 3. How they coordinate: the job board

Each order has a list of **jobs**. A job is one task the host gave the designer:

```
{ id, task, status: queued | working | reporting | done | failed, progress: ["set guests 20 → 10", ...],
  report: { summary, questions, changes, dropped }, createdAt, finishedAt }
```

1. The customer writes. The **host** runs (one short turn). If the message needs work on the order, it calls `ask_designer` with a precise task and replies at once ("On it, I've asked our designer to resize it").
2. The **designer** picks up the job in the background. Each tool call adds a progress line, which the customer sees live.
3. The designer ends with `report`. Its changes are committed as in devlog 05 (checker, conflict check and retry, one Undo group).
4. The report **triggers the host** again. The host tells the customer what was done in plain words, and asks the designer's questions if any.
5. If the customer writes while a job runs, the host sees the board ("job 3: working, set guests 20 → 10") and can answer ("Still on it, the guests are updated, it's resizing now"), or queue another job. Jobs for one order run one at a time, in order.

The chat shows the handoffs as their own lines: "Host → Designer: …" and "Designer → Host: …". The baker's transcript shows them too.

Panel changes still get a short acknowledgement from the host, with no tools.

## 4. What changes for the customer

- The reply to a message is quick (the host only), and the cake updates a moment later as the designer works.
- The chat header shows both agents and what the designer is doing.
- The chat box stays open while the designer works. The panel is paused while a job runs (as in devlog 05), so the two don't race.
- The browser polls the order while a job is open. Server-sent events would be smoother, but polling is enough for one order at a time and is simpler to test.

## 5. Failures

- The host fails: the message gets "The assistant didn't answer. Try again." (as before).
- The designer fails, or stops at the tool limit: the job is marked failed or reports what it did; the host tells the customer. Changes already checked stay only if the designer reported (a failed job commits nothing).
- The host fails while reporting: a plain note from the report is used ("Done: guests 20 → 10; size 10in → 8in").
- The server restarts mid-job: an open job older than 2 minutes is shown as failed.
