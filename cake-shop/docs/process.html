Process overview

How every iteration of the Cake Order Desk is run.

The development cycle

Every software project moves through the same broad stages. Each pass around the loop is an iteration. Every iteration has its own tab on the left and uses the same template, so the process stays the same while the scope changes. These pages are our single record of what we decided at each stage and why.

Stage 1 – Requirements

Question answered: What should the system do, and for whom?

Output: a list of actors and use cases, each with a priority, agreed with the "client" (the class). See the Requirements section of an iteration.

Stage 2 – Design

Question answered: How will it be structured and what will it look like?

Output: done in three phases. 2A Graphic design: screens, navigation and clickable mockups of what the user sees. 2B Software design: data model, web technology decisions, code structure and the functions we will build. 2C Test plan: how we will prove it works. See the Design section of an iteration.

Stage 3 – Implementation

Question answered: Can we build it?

Output: working code for the "Must have" use cases, built in small steps, one use case at a time.

Stage 4 – Testing

Question answered: Does it do what the requirements said?

Output: for each use case, a check that its main flow and alternative flows actually work. Every run of the whole test plan is saved as a dated test result. Each failure, or each item that needs a person to judge it, becomes a ticket (report, investigation, solution, verification) that is closed only when a later run proves it. See the Testing section of an iteration.

Stage 5 – Deployment

Question answered: How do real users get it?

Output: the prototype published at a URL (for example GitHub Pages), or, when the iteration is only for the class, run on local host. Either way, write down where it runs and how to start it.

Stage 6 – Review & Maintenance

Question answered: What did we learn, and what comes next?

Output: a retrospective, the deferred ideas that become the next cycle's requirements, a decision on whether the product is maintained or retired, and a one-page summary report of the whole iteration.

Teaching point: real projects rarely go in a straight line. Testing often reveals a missing requirement, which sends us back to Stage 1. Each stage's output is the next stage's input, which is why we write things down.

Iteration 1 – Ordering desk (Stage 1 of the business)

Goal: an orchestrator that runs a chain of AI, rule and human agents to turn a customer's free-text cake request into a confirmed order, with the baker approving the orders that need it.

Visual: the business and its life cycle, data model (one table) · Devlog: business life cycle and stage contracts

Built: the ordering app is in app/: customer studio, baker inbox, and two AI agents, a host (Haiku 5.5) that talks with the customer and a designer (Sonnet 5.5) that changes the order through the checker, coordinating through a job board. Devlogs: the app build, the assistant as a tool user, and test flows, two agents, a host and a designer.

Two kinds of "stage" on this page. The development stages (Requirements, Design, …) are how we build software. The business stages (Ordering, Production, Fulfillment, Done) are how a cake order moves through the bakery. This iteration runs all six development stages for one business stage: Ordering.

Every run of the test plan is saved as a dated file in test-result/. Each failure or "needs review" item gets a ticket in tickets/; a ticket is closed only when a later run passes. Stage 4 is signed off when every exit criterion of the test plan is met.

Each flow written in Stage 1 becomes one test case. The plan was made in Phase 2C of Stage 2 (see Test plan) and the tests were written in Stage 3; this stage runs them and reports the results. A failure either sends us back to fix code, or back to Stage 1 if the requirement was wrong.
