# job-board: AI model for match scoring

**Type:** Decision record

**Date:** 2026-11-04

**Status:** Draft

**Iteration:** Iteration 2, Stage 2 Design (see [process.html](../../docs/process.html))

**Scope:** Which AI model and which way of calling it the match scoring feature uses, how the key is held, and how it is tested. Not covered: the scoring design itself (see the parent devlog) or hosting.

**Depends on:** [20261104-01-ai-match-scoring.md](20261104-01-ai-match-scoring.md) (Q6).

---

## Context

The scoring feature needs a model that can read a job posting, write up to five criteria, give each a level (Meets, Partly, Does not meet, Unknown) with a short reason, and return them in a fixed shape. Jev was looked at first and rejected as the only model: it writes no reasons and cannot write the criteria itself (parent devlog, Q6).

---

## Decision

### Agreed

- **Claude Haiku 5.5** (`claude-haiku-5-5`) (agreed 2026-11-04). Small, fast and cheap enough that scoring a whole result list in a class demo costs very little (listed at $0.10 per million input tokens and $0.50 per million output tokens for prompts up to 100K tokens).

### Proposed

| Part | Choice | Why |
|---|---|---|
| Where it is called | The **Node server** only | The key never reaches the browser; the web app asks the server to score |
| How | The official **`@anthropic-ai/sdk`** (TypeScript, same as the rest of the app) | One language; typed requests and responses |
| Output shape | **Structured output** (`output_config.format` with a JSON schema) | The reply always matches our shape, which is the type-safe idea from Q8. The shape is a list of at most five items, each with `criterion`, `level` (one of the four), and `reason` |
| One call per job | Each job in the list is scored by its own call, run in parallel | A failure affects only one card (UC-14), and cards fill in as calls finish |
| Key | Read from the `ANTHROPIC_API_KEY` environment variable, set locally in `app/.env` (git-ignored; `app/.env.example` shows the name) | Never in the code or the repository |
| Thinking and effort | Leave Haiku 5.5's default (adaptive thinking, effort `medium`); try `low` if scoring feels slow | Defaults first; tune only if needed |
| Sampling settings | None (no `temperature`, `top_p`, `top_k`) | Haiku 5.5 rejects non-default values |

- **The overall score is computed by our code**, not by the model, from the four levels (parent devlog, Q3). The model only returns levels and reasons.
- **Refusals and errors:** check `stop_reason` before reading the reply. A refusal, an error, a timeout or a reply that does not match the shape marks that one job "not scored". Haiku 5.5 has no automatic server-side fallback to another model, so none is added.
- **Privacy:** the profile and the posting are sent to Anthropic for each scoring click. The seeker is told on the button or profile page (parent devlog, Q7).

## Testing

The model's wording is not repeatable, so tests do not compare text.

- **A fake provider** behind a small interface (`scoreJob(posting, profile) → criteria`) returns fixed criteria. All automated tests (server, API, browser) use it, so they run offline, free and the same every time.
- **Shape checks** on whatever any provider returns: at most five criteria, every level one of the four, every reason non-empty, and the overall score calculated correctly from the levels (Meets 1, Partly 0.5, Does not meet 0, Unknown left out).
- **Failure cases** with the fake: one job fails, all fail, timeout, empty profile, a posting with no clear criteria.
- **Live check (manual, needs a key):** score the demo seeker's results with the sample profile ([sample-profile-alex-chen.md](assets/sample-profile-alex-chen.md)) and read the criteria and reasons: do they come from the posting and quote the profile?

---

## Alternatives considered

- **TypeSafe Jev:** fast and cheap, but gives numbers with no reasons and cannot write the criteria (parent devlog, Q6). Could be revisited as a second step.
- **A larger Claude model (Sonnet or Opus):** probably more careful criteria and reasons, at higher cost and slower. Easy to switch later because the model is one setting. Try it if Haiku's criteria look weak.
- **Calling the model from the browser:** would expose the key. Rejected.

---

## Open questions

### Q1: Is Haiku good enough at reading postings?

Unknown until we see results. If the criteria or reasons look weak in the live check, try a larger model before changing the design.
