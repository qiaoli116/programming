Test plan: AI match scoring

Proposed  For review at the Stage 2 sign-off.

Based on use cases UC-10 to UC-14 and the iteration 2 mockups. The tests are placed in phases in the spec. Iteration 1's 32 test cases and 6 security tests must keep passing (iteration 1 plan). Results of each run go in docs/iteration-2/test-result.

1. Scope

In scope

  • UC-10 to UC-14, including the failure cases
  • The scoring rules: levels, overall score, five-criteria limit
  • Permissions on the new endpoints, and key handling
  • That scoring never changes the stored data or the keyword list

Out of scope (iteration 2)

  • Whether the AI's judgement is right, beyond a manual read (see section 2)
  • UC-15 (Could): editing the profile and scoring again already works, with no new feature
  • Speed and cost under load
  • Browsers other than Chrome

2. How we test something that is not repeatable

The AI's wording changes every time, so no automated test compares its text. Automated tests use a fake provider that returns fixed, predictable criteria (title tags [FAIL], [NONE], [BAD] trigger a failure, no criteria, and an invalid answer). They check the parts that are our code: the answer check, the overall score, parallel running, failures, permissions and screens.

Tested automatically (fake AI)

  • Shape: at most five criteria, valid levels, non-empty reasons
  • The overall score arithmetic
  • Every failure path in UC-14
  • Screens, sorting and disclaimers

Checked by a person (real AI, needs a key)

  • Do the criteria come from the posting?
  • Do the reasons quote the profile, or say it is silent?
  • Do the levels look sensible for the sample profile?

The live checks are marked L in the tables. They are run once at the end of Stage 3 and again in Stage 4, and the verdict is written in the test result. They are a judgement, not a pass or fail number.

4. Test environment and data

  • Same as iteration 1: a fresh in-memory SQLite database per run, re-seeded, accounts by role.
  • The demo seeker (Alex Chen) gets the sample profile in tests that need a saved profile; another seeker has none.
  • The seed data gains no new jobs. The failure tests add their own jobs with [FAIL], [NONE] and [BAD] in the title.
  • The automated suite never needs a key and never makes a network call to the AI.

5. Entry and exit criteria

Entry: start Stage 4 when

  • UC-10 to UC-14 are built
  • The suite passes offline with no key
  • One live run has been done with a real key

Exit: Stage 4 is done when

  • Every test case in section 6 and every test in section 7 passes
  • All iteration 1 tests still pass
  • The manual checklist and the live read are done and written up
  • No known bug blocks a use case

8. Manual checklist (Stage 4)

  • Each new screen matches its mockup (S-09, S-01, S-02), including the disclaimer wording
  • The new screens are usable in a narrow, phone-width window
  • Score levels are readable without colour (the level is also written as text)
  • Wording of "not scored", "unavailable" and "complete your profile" messages is clear and polite
  • Live read (TC-11-10, TC-12-6): score the demo seeker's results with the sample profile and write down what looks wrong
  • Scoring a list of 20 jobs finishes in a time the class can wait for (note the actual time)

9. Reporting

Stage 4 results are saved in docs/iteration-2/test-result, one file per run: date, build, pass or fail for each test case id, the live read notes, bugs found and their fix status.
