Process overview

How every iteration of the Job Board prototype is run.

The development cycle

Every software project moves through the same broad stages. Each pass around the loop is an iteration. Every iteration has its own tab on the left and uses the same template, so the process stays the same while the scope changes. These pages are our single record of what we decided at each stage and why.

Stage 1 – Requirements

Question answered: What should the system do, and for whom?

Output: a list of actors and use cases, each with a priority, agreed with the "client" (the class). See the Requirements section of an iteration.

Stage 2 – Design

Question answered: How will it be structured and what will it look like?

Output: done in three phases. 2A Graphic design: screens, navigation and clickable mockups of what the user sees. 2B Software design: data model, web technology decisions, code structure and the functions we will build. 2C Test plan: how we will prove it works. See the Design section of an iteration.

Stage 3 – Implementation

Question answered: Can we build it?

Output: working code for the "Must have" use cases, built in small steps, one use case at a time.

Stage 4 – Testing

Question answered: Does it do what the requirements said?

Output: for each use case, a check that its main flow and alternative flows actually work.

Stage 5 – Deployment

Question answered: How do real users get it?

Output: the prototype published at a URL (for example GitHub Pages).

Stage 6 – Review & Maintenance

Question answered: What did we learn, and what comes next?

Output: a retrospective, and the deferred ideas that become the next cycle's requirements.

Teaching point: real projects rarely go in a straight line. Testing often reveals a missing requirement, which sends us back to Stage 1. Each stage's output is the next stage's input, which is why we write things down.

What is a use case?

A use case describes one goal that one kind of user wants to achieve with the system, written as a short story of steps. It says what the user and system do – not how it is coded. Because it is plain language, the client and developers can both read and agree on it.

Anatomy of a use case on this page

  • Actor – who wants the goal.
  • Goal – what they want to achieve, in one sentence.
  • Preconditions – what must be true before it can start.
  • Main flow – the "everything goes right" steps.
  • Alternative flows – what happens when something differs or goes wrong.
  • Postconditions – what is true when it ends successfully.
  • Priority – chosen with MoSCoW (below).

Scope: a minimal prototype

We deliberately keep the system as small as possible while still being a complete loop: an employer posts a job, a seeker finds it and applies, and both sides can see the result.

Job Seeker can…
  • search for jobs
  • view a job
  • sign in and sign out
  • apply for a job
  • see the list of jobs they applied for
Employer can…
  • sign in and sign out
  • post a job
  • edit their own job posts
  • see the applications for their own jobs

Prioritising with MoSCoW

Every candidate use case was given a priority. After cutting back to the minimum, everything that remains is Must (the prototype is pointless without it). The rest went into the Won't (yet) list below – deliberately left for a later cycle. The two middle categories, Should (important, build if time allows) and Could (nice to have), are empty for now.

UC-01Search for jobsMust
Actor
Job Seeker (signing in is not required)
Goal
Find jobs that match what I'm looking for.
Preconditions
At least one job post exists in the system.
Main flow
  1. The seeker opens the home page.
  2. The seeker types a keyword (job title, skill or company) and/or a location.
  3. The seeker submits the search.
  4. The system shows a list of matching jobs: title, company, location, short summary, date posted.
Alternative flows
  • 2a. Both fields empty: the system shows all jobs, newest first.
  • 4a. No matches: the system says nothing was found and suggests broadening the search.
Postconditions
The seeker sees a results list; no data is changed.
UC-02View job detailsMust
Actor
Job Seeker (signing in is not required)
Goal
Read the full description of a job to decide whether to apply.
Preconditions
The seeker has a job in front of them (from search results or a direct link).
Main flow
  1. The seeker selects a job from the results.
  2. The system shows the full post: title, company, location, work type, salary (if given), description, requirements.
  3. The page offers an "Apply" button and a way back to the results.
Alternative flows
  • 1a. Job does not exist: the system shows a "Job not found" message with a link to search again.
Postconditions
The seeker has read the job; no data is changed.
UC-03Apply for a jobMustrevised
Actor
Job Seeker (signed in)
Goal
Send my application to the employer.
Preconditions
The seeker is signed in (UC-08) and viewing a job (UC-02).
Main flow
  1. The seeker chooses "Apply".
  2. The system shows an application form. It shows who is applying (name and email, taken from the seeker's account) and asks for a phone number (optional) and a cover letter.
  3. The seeker fills in the form and submits it.
  4. The system validates the form and records the application against the seeker's account.
  5. The system confirms: "Your application has been sent."
Alternative flows
  • 1a. Not signed in: the system sends the seeker to sign in (UC-08) and then back to this job.
  • 4a. Cover letter missing: the system highlights the problem and keeps what the seeker already typed.
  • 4b. The seeker has already applied to this job: the system tells the seeker and does not create a duplicate.
Postconditions
A new application is linked to the job and to the seeker's account, and is available to the job's employer (UC-07) and to the seeker (UC-04).
UC-04View my applicationsMustrevised
Actor
Job Seeker (signed in)
Goal
See the list of jobs I have applied for.
Preconditions
The seeker is signed in (UC-08). There is no need to type an email: the system knows who is signed in.
Main flow
  1. The seeker opens "My applications".
  2. The system lists every application made by this seeker: job title, company, date applied.
  3. The seeker can select an entry to view the job (UC-02).
Alternative flows
  • 1a. Not signed in: the system sends the seeker to sign in (UC-08).
  • 2a. No applications yet: the system says so and invites the seeker to search for jobs.
Postconditions
No data is changed. A seeker never sees another seeker's applications.
UC-05Post a jobMustrevised
Actor
Employer (signed in)
Goal
Advertise a vacancy so job seekers can find it.
Preconditions
The employer is signed in (UC-08) with an employer account.
Main flow
  1. The employer chooses "Post a job".
  2. The system shows a form: title, location, work type, salary range (optional), description, requirements. The company name is filled in from the employer's account and cannot be changed.
  3. The employer fills in and submits the form.
  4. The system validates and saves the post, owned by this employer.
  5. The system shows the new post as job seekers will see it.
Alternative flows
  • 1a. Not signed in, or signed in as a seeker: the system sends the user to sign in (UC-08) or says the area is for employers.
  • 4a. Required field missing: the system highlights it and keeps the other values.
Postconditions
The job appears in search results (UC-01) under the employer's company name.
UC-06Edit a job postMustrevised
Actor
Employer (signed in)
Goal
Correct or update a job post after publishing it.
Preconditions
The employer is signed in (UC-08) and owns the post (UC-05).
Main flow
  1. The employer opens the employer area, which lists their own job posts.
  2. The employer selects a post and chooses "Edit".
  3. The system shows the same form as UC-05, filled with the current values.
  4. The employer changes fields and saves.
  5. The system validates and saves the changes.
Alternative flows

  • 5a. Required field missing: same behaviour as UC-05 step 4a; nothing is saved until it is fixed.
Postconditions
Seekers see the updated post in search results and job details. Applications already received are kept.
UC-07View applications for a jobMustrevised
Actor
Employer (signed in)
Goal
See who applied to my job.
Preconditions
The employer is signed in (UC-08) and owns the post (UC-05). Applications appear once seekers have applied (UC-03).
Main flow
  1. The employer opens the employer area and selects one of their posts.
  2. The system lists the applications for that post: applicant name, email (both from the applicant's account), date applied.
  3. The employer opens an application to read the full details and cover letter.
Alternative flows
  • 1a. The post belongs to another employer: the system refuses ("You cannot view these applications") and shows nothing.
  • 2a. No applications yet: the system says so.

UC-08Sign inMust
Actor
Job Seeker or Employer
Goal
Prove who I am so I can apply, see my applications, or manage my job posts.
Preconditions
An account exists. In the prototype accounts are pre-created; there is no sign-up.
Main flow
  1. The user chooses "Sign in", or is sent to the sign-in screen from a page that needs it (for example "Apply").
  2. The system shows the sign-in form: email and password.
  3. The user fills in the form and submits it.
  4. The system checks the email and password and starts a session.
  5. The system takes the user where they were heading. If they were heading nowhere in particular, a seeker goes to the home page and an employer to "My job posts".
Alternative flows
  • 1a. Already signed in: the system goes straight to the user's start page.
  • 3a. A field is empty: the system highlights it.
  • 4a. Wrong email or password: the system says "Email or password is incorrect" (without saying which), keeps the email and clears the password.
Postconditions
The user is signed in. The header shows their name, their role and a "Sign out" button.
UC-09Sign outMust
Actor
Job Seeker or Employer
Goal
End my session so the next person on this device cannot use my account.
Preconditions
The user is signed in (UC-08).
Main flow
  1. The user chooses "Sign out" in the header.
  2. The system ends the session.
  3. The system shows the sign-in screen with the message "You have been signed out."
Alternative flows
  • 2a. The session had already expired: the result is the same.
Postconditions
Pages that need an account ask the user to sign in again.

Open questions for the class (the "client")

  1. Accounts are pre-created and every demo account shares one password. Is that acceptable for a demo? What would real users need (sign-up, email verification, password reset)?
  2. Is salary compulsory when posting a job, or optional?
  3. Should employers see applicants' contact details immediately?
  4. What is the one use case we would regret not building?
  5. Have we missed an actor or a goal entirely?

Phase 2B – Software design decisions made

Question answered: What will the code be made of, and which web technologies do we choose? Once code exists, changing these decisions is expensive. That is why we make them now, in the open, with reasons.

This is a multi-user application, so besides the screens and the data we must also decide the database, the backend, the frontend, how users sign in, and who may do what.

The system stores three kinds of thing. Everything on the screens above comes from one of them. Updated for sign-in (decision 18): User was added, and Job and Application now point at the users involved instead of holding a company name, name and email.

Relationships and rules
  • One employer (User) has many Jobs: Job.ownerId. The company name shown on a job is the owner's companyName.
  • One Job has many Applications: Application.jobId.
  • One seeker (User) has many Applications: Application.applicantId.
  • UC-03 4b: the pair (jobId, applicantId) must be unique, which stops duplicate applications.
  • UC-04 finds the Applications whose applicantId is the signed-in user. UC-07 shows each applicant's name and email by looking up their User.
  • Permissions: a Job can be edited, and its Applications read, only by its owner. An Application can be read only by its applicant and by the owner of its Job.

Technology decisions

For each decision we listed the realistic options with their pros and cons and marked a recommendation. The class adopted the recommendation every time; the chosen option is highlighted on each card. Keeping the rejected options on the page records why we chose, which matters when we revisit a decision later.

T-1 Architecture: where does the data live?

The app now has many users, so an employer on one computer must see applications sent from another. This reopens decision 7 (browser-only).

Decision: Frontend + backend + database

T-2 Backend: language and framework

The server code that receives requests, applies the rules and talks to the database.

Not listed (Java Spring Boot, C# ASP.NET, PHP Laravel…)? Say so and we add it.

Decision: Node.js + Express

T-3 Database

Where jobs, applications and users are stored. Our data model has two linked kinds of thing (jobs and their applications), and users once accounts exist.

Decision: SQLite

T-4 API style: how the pages and the server talk

The "contract" between what the user sees and the code that holds the data.

Decision: REST API with JSON

T-5 Frontend

How the screens are built and how they call the API. Ignore this one if T-4 is server-rendered pages. Revised: first decided as plain HTML + JavaScript, then changed to React because starting with a framework costs little now and avoids the biggest rewrite later (decision 17). The language is TypeScript on both the frontend and the backend.

Decision: React (with Vite and TypeScript)

T-6 Authentication: how users prove who they are

Needed as soon as different people use the app. This changes Stage 1 (see the box below).

Decision: Email + password, session cookie

T-7 Authorization: roles and ownership

Once users exist: who is allowed to do what.

Rules that apply whichever option is chosen: an employer can edit a job and see its applications only if they posted it; a seeker can see only their own applications; every one of these checks happens on the server, never only in the page.

Decision: Two roles, set on the account

T-8 Hosting

Where the backend and database run. This is carried out in Stage 5, but it limits earlier choices (for example SQLite on a free host).

Decision: Cloud platform (Render, Railway, Fly.io)

Migration: making the move doable

Because the prototype already uses TypeScript and React, the two stacks differ in only two places: the database and hosting. Authentication is upgraded rather than replaced, and the frontend grows rather than being rewritten. Everything else carries over unchanged. For each move, here is how hard the move is and what we do now so that it stays that hard and no harder.

The database move is a dialect change plus a data copy, and the rest is configuration or incremental upgrades. How the seed data is delivered

  • One data file, one script. The data lives in a single readable file (for example seed/seed-data.json). A command such as npm run seed loads it into the database.
  • Repeatable. The same command can wipe and reload, so the demo can be reset to a known state before each class.
  • Dates relative to today. The script writes "posted 3 days ago" as a real date computed at load time, so the list never looks stale.
  • Demo logins. All seeded accounts share one demo password, listed in the README and shown as a hint on the Sign in screen. Passwords are stored hashed like any other.
  • Demo only. The production iteration must not ship known passwords. There the seed script is limited to development and test environments, and real users sign up themselves.
  • Migration-friendly. The seed goes through the repository modules, not raw SQL, so the same script works unchanged on SQLite now and PostgreSQL later.
Security basics – not up for debate. Passwords are stored only as salted hashes, never as text. The server re-checks all input and all permissions, because the browser cannot be trusted. Database queries use parameters, not string-joining. The deployed site uses HTTPS.

Architecture: four layers and the browser

Splitting the code into layers means each part has one job. This is also why the database (SQLite now, PostgreSQL later) and the frontend can be replaced without touching the rest. Everything below is a proposal for the class to review; no code exists yet.

BROWSER        React app (Vite, TypeScript)        screens S-01 to S-08 built from components
  |  HTTP + JSON, session cookie, under /api/v1       the only contract between the two halves
  v
ROUTES         Express routes and middleware       URL in, JSON out. Checks "signed in?" and "which role?",
  |                                                validates the shape of the input, picks the status code
  v
SERVICES       signIn, searchJobs, applyToJob ...  the business rules: validation, who owns what,
  |                                                the duplicate-application rule
  v
REPOSITORIES   users, sessions, jobs, applications the only code that contains SQL (via Knex)
  |
  v
DATABASE       SQLite file now, PostgreSQL later
Rules that keep it tidy. A layer may only call the layer directly below it. A route never touches the database; a page never talks to the database or to another page's code; only repositories contain SQL. The browser and the server share one set of TypeScript types (User, Job, Application, request and response shapes), so a change to the API is caught by the compiler on both sides. In production Express also serves the built React files, so there is one service to deploy. While developing, Vite serves the page and forwards /api requests to Express.
